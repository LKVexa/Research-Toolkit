# Installation and environment

Keep the whole versioned application together. The package pins the application, fixed adapters, qualification artifacts, synthetic datasets, and embedded shared foundation. It is a separate local Windows product; no sibling application or original delivery must be edited to install it.

Required runtime:

| Dependency | Required environment |
| --- | --- |
| Operating system | Windows |
| Python | 3.12.14, launched in isolated mode with bytecode writes disabled |
| NumPy | 2.3.5 for the qualified foundation Python fixture |
| .NET | The Windows .NET Framework runtime required by the pinned foundation C# diagnostic |
| Shared foundation | Version 0.1.0-rc.1, exact manifest pin recorded in the package |

The authored numerical methods themselves use Python's standard library. The native Python fixture uses the existing pinned NumPy environment. Normal operation does not install dependencies, download files, use a model/provider account, or make network calls. Use an already available compatible runtime; do not silently upgrade dependencies to bypass an environment mismatch.

From the application directory, use `Start-Research.ps1` in PowerShell or `Research-Toolkit.cmd` from Windows. The portable entry point is `research.py`. Direct invocation must use the compatible Python executable with `-I -B`:

```powershell
& 'C:\Path\To\Python312\python.exe' -I -B './research.py' catalog
```

The executable path above is a placeholder for an existing Python 3.12.14 installation, not an installation command. See the launcher source for runtime discovery. Use its configured runtime rather than the Windows Store alias.

Use short, distinct paths for the application, state, and exports. The bundled foundation and run evidence use nested paths, so a deeply nested Windows destination can exceed filesystem path limits even when the top-level command is valid. A short state path such as `$env:LOCALAPPDATA\RT01` is preferable to a state folder inside a long project checkout. Keep state outside the application, original delivery trees, shared-foundation release, workbench, and coding-agent release. The tool rejects protected-root overlap and unrelated or incompatible state folders.

Do not alter files inside a released application. Changed, missing, or unexpected package artifacts invalidate verification. Keep generated bytecode, credentials, caches, test work directories, and mutable run state outside the shipped application. Preserve the entire known-good release for rollback.

Installation status and experiment outcomes are distinct. The release evidence records acceptance against an exact package and environment; merely opening the catalog does not establish successful experiments or paper replication.
